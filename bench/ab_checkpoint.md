# 对照实验:checkpoint_channel_mode = full vs delta

日期:2026-11-06 · 提交:cef5732 · 脚本:bench/ab_run.sh、bench/ab_setup.py、bench/load.py

## 目的
量化上游已提供的 `delta` 检查点模式相对默认 `full` 模式,在数据库体积与吞吐上的差异。

## 方法
- 每次实验使用全新的 SQLite 数据库(独立目录),避免旧数据污染体积对比
- 同一份配置(仅 mock 模型;标题、建议、摘要、记忆已关闭),仅 `checkpoint_channel_mode` 不同(delta 的 snapshot_frequency 取默认值 10)
- 每次:先预热 3 次,再 300 次运行、并发 10;full 与 delta 交替各 3 次
- 单机:Windows 10 + WSL2(6 GB、8 核),压测脚本、mock、Gateway 同机运行

## 结果(3 次重复)
| 指标 | full | delta |
|---|---|---|
| 吞吐(次/秒) | 2.33 / 2.33 / 2.31 | 2.31 / 2.30 / 2.28 |
| 总耗时 p50 | 4.32 / 4.24 / 4.29 s | 4.32 / 4.31 / 4.33 s |
| 总耗时 p95 | 5.38 / 5.47 / 5.40 s | 5.32 / 5.50 / 5.51 s |
| 数据库大小 | 47.8 / 47.7 / 47.6 MB | 41.1 / 41.1 / 41.1 MB |
| checkpoint 列 | 32.6 MB | 25.5 MB |
| 每次运行体积 | 约 161 KB | 约 139 KB |
| 检查点行数 | 7,272 | 7,272 |

## 结论(谨慎表述)
1. 体积:此场景下 delta 使 checkpoint 列减少约 22%、整库减少约 14%;3 次结果高度一致(波动 < 0.3%)。
2. 行数不变:两种模式每次运行都产生约 24 个检查点,delta 减小的是单个检查点的大小,而非数量。
3. 吞吐与延迟:未观察到有意义的差异(平均 2.32 对 2.30 次/秒,约 1%,样本仅 3 个,不足以统计检验)。

## 局限
- 每个对话只有 1 条消息;delta 的预期优势在长对话,本实验未覆盖,不能外推
- 只测了写入路径,未测读取历史、分支、重新生成,而上游注释指出 delta 的代价是读取时重建更慢
- mock 固定输出,不代表真实模型;单机同机运行,绝对值只有相对意义
- delta 的快照间隔只测了默认值 10
- 与上游留存契约(backend/docs/checkpoint-retention-contract.md)的关系:检查点构成父链,不自行实现清理
