# 对照实验:checkpoint_channel_mode = full vs delta

日期:2026-11-06 · 提交:cef5732 · 脚本:bench/ab_run.sh、bench/ab_setup.py、bench/load.py

## 目的
量化上游已提供的 `delta` 检查点模式相对默认 `full` 模式,在数据库体积与吞吐上的差异。

## 方法
- 每次实验使用全新的 SQLite 数据库(独立目录),避免旧数据污染体积对比
- 同一份配置(仅 mock 模型;标题、建议、摘要、记忆已关闭),仅 `checkpoint_channel_mode` 不同(delta 的 snapshot_frequency 取默认值 10)
- 每次:先预热 3 次,再 300 次运行、并发 10;full 与 delta 交替各 3 次
- 单机:Windows 10 + WSL2(6 GB、8 核),压测脚本、mock、Gateway 同机运行

## 结果(3 次重复)
| 指标 | full | delta |
|---|---|---|
| 吞吐(次/秒) | 2.33 / 2.33 / 2.31 | 2.31 / 2.30 / 2.28 |
| 总耗时 p50 | 4.32 / 4.24 / 4.29 s | 4.32 / 4.31 / 4.33 s |
| 总耗时 p95 | 5.38 / 5.47 / 5.40 s | 5.32 / 5.50 / 5.51 s |
| 数据库大小 | 47.8 / 47.7 / 47.6 MB | 41.1 / 41.1 / 41.1 MB |
| checkpoint 列 | 32.6 MB | 25.5 MB |
| 每次运行体积 | 约 161 KB | 约 139 KB |
| 检查点行数 | 7,272 | 7,272 |

## 结论(谨慎表述)
1. 体积:此场景下 delta 使 checkpoint 列减少约 22%、整库减少约 14%;3 次结果高度一致(波动 < 0.3%)。
2. 行数不变:两种模式每次运行都产生约 24 个检查点,delta 减小的是单个检查点的大小,而非数量。
3. 吞吐与延迟:未观察到有意义的差异(平均 2.32 对 2.30 次/秒,约 1%,样本仅 3 个,不足以统计检验)。

## 局限
- 每个对话只有 1 条消息;delta 的预期优势在长对话,本实验未覆盖,不能外推
- 只测了写入路径,未测读取历史、分支、重新生成,而上游注释指出 delta 的代价是读取时重建更慢
- mock 固定输出,不代表真实模型;单机同机运行,绝对值只有相对意义
- delta 的快照间隔只测了默认值 10
- 与上游留存契约(backend/docs/checkpoint-retention-contract.md)的关系:检查点构成父链,不自行实现清理

## 后续
- 多轮长对话场景下重测体积
- 测读取历史的延迟,量化 delta 的重建成本
- 扫描 snapshot_frequency

# 补充:多轮对话与并发写锁(2026-11-06 晚)

## 多轮对照(并发 3,100 个对话 x 8 轮 = 800 次运行,全新 SQLite)
| 指标 | full | delta | 差异 |
|---|---|---|---|
| 服务端运行状态 | 804 success | 804 success | 相同 |
| 检查点行数 | 18,594 | 18,594 | 相同 |
| checkpoint 列 | 195.9 MB | 104.6 MB | -46.6% |
| 数据库合计 | 237.3 MB | 159.4 MB | -32.8% |
| 每次运行体积 | 302.2 KB | 203.0 KB | -32.8% |
| 吞吐(次/秒) | 1.48 | 1.47 | 约 -0.7% |
| 总耗时 p50 / p95 | 1.922 / 2.334 s | 1.941 / 2.342 s | +1.0% / +0.3% |

节省比例随对话变长而增大:1 轮时整库 -14%(checkpoint 列 -22%),8 轮时整库 -33%(checkpoint 列 -47%)。8 轮结果每种模式仅测 1 次(1 轮结果为 3 次重复)。

## 观察:并发 10 的多轮场景下 SQLite 写锁冲突
- 同样 100 x 8 的负载,并发 10 时服务端 runs 表中约 78% 的运行为 error(full:631 error / 173 success),日志错误均为 `sqlite3.OperationalError: database is locked`(langgraph sqlite aio.aput 写检查点)。并发降到 3 后 804 个运行全部 success、日志 0 错误。
- 客户端只检查"HTTP 200 + 收到 end 事件"时,800/800 显示成功:服务端把存储错误作为流的正常结束返回。因此压测汇总必须核对服务端 runs 表状态,存在非 success 即作废。
- 单轮场景(每对话 1 次运行)并发 10 下 900 次运行日志 0 错误,说明冲突与"同一对话相邻两轮连续发起"有关(推测:相邻两轮的收尾写入与下一轮写入争抢写锁,未验证)。
- 只测了并发 3 与 10 两点,不能据此断言安全并发度;上游文档称 SQLite 面向单节点部署,多 worker 使用 Postgres。

## 对此前结论的修正
- 并发 10 的多轮实验(含 delta)全部作废(日志错误 631/762 行),其体积与吞吐数据不得引用。
- 单轮三次重复实验的日志错误均为 0,仍然有效。

## 仍未测量
